# Aula 3.5: Firewalls, portas e portas efêmeras

[[03 - Fundamentos de Redes para a Nuvem|Voltar ao módulo]]

> [!question] Pergunta que esta aula responde
> Quais portas e protocolos aparecem na prova, o que significa um firewall ser stateful ou [[Stateless|stateless]], e por que uma [[Network ACL|network ACL]] exige liberar [[Porta Efemera|portas efêmeras]] para as respostas?

## Por que firewalls e portas existem

Uma máquina com um IP roda dezenas de programas ao mesmo tempo. O IP leva o pacote até ela; a **porta** leva ao programa certo. Um servidor web escuta na porta 443, um banco PostgreSQL na 5432. Se qualquer pessoa na internet pudesse falar com qualquer porta de qualquer máquina, uma porta de administração esquecida (SSH, RDP, banco de dados) seria a porta de entrada de um ataque. Daí o **firewall**: um filtro que decide, por **origem, destino, protocolo e porta**, o que passa.

Na AWS há dois firewalls básicos de rede, com propriedades opostas, e a prova adora a diferença: [[Security Group]] e [[Network ACL]]. Para entender a diferença, é preciso primeiro entender portas e o que é "estado".

## Portas: o endereço do programa

A **porta** é um número de 16 bits (0 a 65535) dentro de [[TCP]] ou [[UDP]]. Uma conexão fica identificada por cinco informações, a **5-tupla**: protocolo, IP de origem, porta de origem, IP de destino, porta de destino.

- O **servidor** escuta em uma porta conhecida (443 para HTTPS).
- O **cliente** não escolhe uma porta conhecida: o sistema operacional sorteia uma **[[Porta Efemera|porta efêmera]]** (ephemeral port, alta) como porta de origem, e é nela que a resposta volta.

As faixas costumam ser: 0 a 1023 "bem conhecidas" (well-known), 1024 a 49151 "registradas" e o restante para uso dinâmico. A faixa de [[Porta Efemera|portas efêmeras]] exata depende do sistema operacional (veremos adiante).

> [!example] Mapeando um aplicativo em portas
> Uma API NestJS atrás de um [[Application Load Balancer|ALB]], com PostgreSQL e Redis: o ALB escuta em 443 (do mundo); a API escuta em 3000 (só do ALB); o [[RDS]] escuta em 5432 (só da API); o cache, em 6379 (só da API). Cada seta é uma regra "de quem, para qual porta". O desenho de um [[Security Group|security group]] por camada vem direto daí.

## O que é "estado" em um firewall

Uma conexão [[TCP]] é uma conversa de duas vias: a requisição vai do cliente ao servidor e a resposta volta pelo caminho inverso, com portas trocadas.

- **[[Stateful e Stateless (Firewall)|Firewall stateful]]** (com estado): guarda uma tabela das conexões que ele deixou passar. Se a requisição foi permitida, a **resposta é permitida automaticamente**, sem regra adicional. Você escreve uma regra por direção de iniciação.
- **[[Stateful e Stateless (Firewall)|Firewall stateless]]** (sem estado): trata cada pacote de forma isolada, sem memória. A resposta é só mais um pacote e precisa de **regra própria** na direção inversa.

Essa distinção explica a diferença de configuração entre os dois firewalls da AWS.

## Security group: stateful, no recurso, só permite

A documentação da AWS descreve o [[Security Group|security group]] como um firewall virtual que controla o tráfego que **entra e sai dos recursos aos quais está associado** (na prática, da interface de rede, [[ENI]], da instância). Pontos confirmados (verificado em novembro de 2026):

- **[[Stateful e Stateless (Firewall)|Stateful]]:** se uma instância envia uma requisição, a resposta é permitida independentemente das regras de entrada; respostas a tráfego de entrada permitido saem independentemente das regras de saída.
- Só tem regras de **permissão** (allow). Não existe regra de negar. O que não é explicitamente permitido é negado.
- Todas as regras são avaliadas em conjunto; **não há ordem**: se qualquer uma permite, passa.
- Pode ser associado a vários recursos, e um recurso pode ter vários [[Security Group|security groups]] (o resultado é a união das permissões).
- Não tem custo adicional.
- Uma regra de entrada pode ter como origem um **[[CIDR|bloco CIDR]]** ou **outro [[Security Group|security group]]** (o que permite dizer "só quem estiver no SG do [[Application Load Balancer|ALB]] acessa a API", sem depender de IPs).
- **Não filtra** tráfego de/para o [[DNS]] da Amazon, DHCP, metadados da instância ([[Instance Metadata Service|IMDS]]), metadados de [[Tarefa ECS|tarefas do ECS]], ativação de licenças do Windows, Amazon Time Sync Service e IPs reservados pelo roteador da [[VPC]].

Um [[Security Group|security group]] recém-criado por você começa sem regras de entrada (nada entra) e, por padrão, com saída liberada para todos os destinos (confira ao criar; é o comportamento padrão documentado).

**O [[Security Group|security group]] padrão da [[VPC]] (default).** Toda VPC nasce com um security group chamado `default`, que você pode editar mas não apagar. Se você lança uma instância sem escolher security group, ela entra no `default` (verificado em novembro de 2026). Regras originais:

| Direção | Origem ou destino | Efeito |
|---|---|---|
| Entrada | o **próprio** [[Security Group\|security group]] `default` (protocolo e portas: todos) | Recursos que estão no mesmo SG se falam sem regra extra; nada vindo de fora (internet, [[NAT Gateway\|NAT gateway]]) entra |
| Saída | `0.0.0.0/0` (e `::/0` se a [[VPC]] tem [[IPv6]]) | Todo o tráfego de saída liberado |

Pegadinha clássica: "as instâncias no SG default se falam sem regra adicional" é verdade, mas isso não abre acesso da internet. A recomendação da documentação é criar [[Security Group|security groups]] específicos por camada em vez de usar o `default`.

> [!info] Rastreamento de conexões (connection tracking)
> O "estado" do [[Security Group|security group]] é implementado por **[[Connection Tracking|rastreamento de conexões]]**. Um fluxo [[TCP]] ou [[UDP]] **não é rastreado** quando existe regra liberando todo o tráfego (`0.0.0.0/0` ou `::/0`) em uma direção e outra regra liberando todas as respostas (qualquer porta) na direção contrária. Nesse caso a resposta é permitida pela regra, não pelo estado, e remover a regra derruba a conexão existente na hora. Para a prova basta saber: SG é stateful; regras estreitas geram conexões rastreadas. A lista de conexões sempre rastreadas e o limite de conexões por instância ficam na documentação de [[EC2]] (security group connection tracking).

**[[Security Group|Security group]] e Network [[Elastic Load Balancing|Load Balancer]].** Desde 2023 o [[Network Load Balancer]] aceita security groups (antes não aceitava, e material antigo ainda diz "NLB não tem SG"). Três consequências que caem na prova (verificado em novembro de 2026):

- O SG só pode ser associado **na criação** do [[Network Load Balancer|NLB]]; se ele nasceu sem SG, não dá para associar depois. Sem SG, todo o tráfego de cliente chega aos [[Listener|listeners]].
- Com **[[Client IP Preservation|preservação de IP do cliente]]** (padrão em destinos do tipo instância), o destino vê o IP do cliente, não o do [[Network Load Balancer|NLB]]. Por isso o SG dos destinos precisa liberar os IPs dos clientes **ou**, mais simples, referenciar o **SG do NLB** como origem (a regra funciona mesmo com a preservação ligada).
- Os [[Health Check|health checks]] do [[Network Load Balancer|NLB]] seguem as regras de **saída** do SG dele (não as de entrada): bloquear a saída faz os destinos parecerem não saudáveis. Destinos por IP, tráfego de [[PrivateLink]] e [[Gateway Load Balancer]] têm comportamentos próprios, detalhados nos Módulos 7 e 12.

## Network ACL: stateless, na sub-rede, permite e nega

A **[[Network ACL]]** (NACL) é uma lista de regras aplicada na **fronteira da [[Sub-rede|sub-rede]]**: filtra o que entra e sai da sub-rede, não o que circula dentro dela. Pontos confirmados (verificado em novembro de 2026):

- **[[Stateful e Stateless (Firewall)|Stateless]]:** a documentação diz que, se você permite uma entrada específica, as respostas **não** são permitidas automaticamente.
- Tem regras de **permitir e de negar**, cada uma com um número de 1 a 32766, avaliadas **em ordem crescente**; a primeira que casa é aplicada e as outras são ignoradas. Recomenda-se numerar de 10 em 10 ou de 100 em 100 para poder inserir regras depois.
- Toda [[Network ACL|NACL]] tem uma regra final `*` que **nega** tudo o que nenhuma regra anterior casou (não pode ser alterada).
- Cada [[Sub-rede|sub-rede]] está associada a **uma** [[Network ACL|NACL]] (se você não escolher, usa a padrão); uma NACL pode estar associada a várias sub-redes.
- Regras [[IPv4]] e [[IPv6]] são **avaliadas separadamente**.
- Sem custo adicional.
- Não filtra [[DNS]] da Amazon, DHCP, [[Instance Metadata Service|IMDS]], Amazon Time Sync, entre outros (a mesma lista do [[Security Group|security group]]), e não bloqueia o [[Route 53 Resolver]] nem o IMDS. Para filtrar DNS, usa-se o [[Route 53 Resolver DNS Firewall]].
- A [[Network ACL|NACL]] padrão da [[VPC]] permite todo o tráfego de entrada e saída; uma NACL personalizada nova, ao contrário, começa negando tudo até você acrescentar regras.

### Comparação que cai na prova

| | [[Security Group\|Security group]] | [[Network ACL]] |
|---|---|---|
| Onde atua | Recurso ([[ENI\|interface de rede]] da instância, do [[Application Load Balancer\|ALB]], do [[RDS]]...) | [[Sub-rede]] (entrada e saída da sub-rede) |
| Estado | Stateful | [[Stateless]] |
| Tipos de regra | Só permite | Permite e nega |
| Avaliação | Todas as regras juntas | Em ordem numérica, a primeira que casa vence |
| Padrão | Nega entrada e permite saída (SG novo) | [[Network ACL\|NACL]] padrão permite tudo; personalizada nega tudo |
| Origem da regra | [[CIDR]], outro SG ou [[Managed Prefix List\|prefix list]] | Só CIDR |
| Uso típico | Controle principal, por camada | Camada extra, bloquear IPs ou faixas específicas |

Regra de decisão: **para "permitir X para Y", [[Security Group|security group]]; para "bloquear o IP Z", [[Network ACL|NACL]]** (security group não tem negar).

## Portas efêmeras: o ponto onde a NACL pega você

Como a [[Network ACL|NACL]] é [[Stateless|stateless]], para cada conexão você precisa liberar **dois fluxos**: o de ida (para a porta do servidor) e o de volta (para a [[Porta Efemera|porta efêmera]] do cliente).

> [!example] O site que ninguém acessa
> Uma [[Sub-rede Publica|sub-rede pública]] tem [[Network ACL|NACL]] personalizada com apenas estas regras:
> - Entrada: `100` permite [[TCP]] 443 de `0.0.0.0/0`.
> - Saída: `100` permite [[TCP]] 443 para `0.0.0.0/0`.
>
> O usuário abre `https://site`. A requisição entra (443): ok. A instância responde, mas a resposta sai **de** `443` **para** a [[Porta Efemera|porta efêmera]] do navegador (por exemplo `51234`). A regra de saída só permite destino 443, não `51234`: o pacote é descartado e a página não carrega. A correção é uma regra de saída permitindo [[TCP]] 1024-65535 (ou a faixa específica) para `0.0.0.0/0`. O [[Security Group|security group]] da instância não precisaria disso, porque é stateful.

A faixa efêmera depende de **quem inicia** a conexão (a documentação lista, verificado em novembro de 2026):

| Cliente | [[Porta Efemera\|Portas efêmeras]] |
|---|---|
| Muitos kernels Linux (inclusive Amazon Linux) | 32768 a 61000 |
| Windows até o Server 2003 | 1025 a 5000 |
| Windows Server 2008 e posteriores | 49152 a 65535 |
| Requisições originadas do [[Elastic Load Balancing]] | 1024 a 65535 |
| [[NAT Gateway\|NAT gateway]] | 1024 a 65535 |
| Funções Lambda | 1024 a 65535 |

Na prática, para cobrir qualquer tipo de cliente, libera-se `1024-65535` e, se houver porta maliciosa conhecida nessa faixa, coloca-se uma regra de negar **antes** (número menor) que a liberação ampla. Outra consequência: se uma instância da sua [[VPC]] é a **cliente** (baixa pacote de um repositório), a [[Network ACL|NACL]] precisa liberar **entrada** nas [[Porta Efemera|portas efêmeras]] para a resposta voltar.

> [!info] Ligando os pontos
> O [[NAT Gateway|NAT gateway]] (aula 3.4) usa portas 1024-65535 na saída: por isso a [[Network ACL|NACL]] da [[Sub-rede|sub-rede]] onde ele está precisa permitir as respostas nessa faixa. Os [[Health Check|health checks]] de um balanceador também são tráfego que uma NACL mal configurada derruba: a documentação avisa que uma regra de negar tudo vindo de `0.0.0.0/0` ou do [[CIDR]] da sub-rede impede o balanceador de fazer health checks.

## Camadas de defesa e quem faz o quê

Pense em [[Defesa em Profundidade|defesa em profundidade]], de fora para dentro: rota (existe caminho?), [[Network ACL|NACL]] (a [[Sub-rede|sub-rede]] aceita?), [[Security Group|security group]] (a instância aceita?), firewall do sistema operacional (ex.: `iptables`), aplicação (está escutando?). Cada camada pode ser a que bloqueia. O método de diagnóstico é percorrer essa lista na ordem. A aula 3.1 lembrou que security group e NACL enxergam só IP, protocolo e porta: ataques de aplicação ([[SQL Injection|SQL injection]]) são do [[WAF]].

Um cuidado de arquitetura frequente: portas de administração. Em vez de abrir a 22 ou 3389 para a internet, a abordagem moderna é não abrir nenhuma e usar o [[Session Manager]] do [[Systems Manager]] (acesso pelo agente, auditado, sem IP de entrada). O Módulo 6 detalha [[Bastion Host|bastion host]] versus Session Manager.

## Como isso cai na prova

Tasks do exam guide cobertas: **1.2** (control ports, protocols, and network traffic; [[Security Group|security groups]], [[Network ACL|network ACLs]], segmentação) e **3.4**.

**Padrões de cenário**
- "Permitir só o tráfego do [[Application Load Balancer|ALB]] para as instâncias": regra de entrada com o [[Security Group|security group]] do ALB como origem.
- "Bloquear um endereço IP específico ou uma faixa": regra de negar em uma [[Network ACL|network ACL]].
- "Após adicionar uma [[Network ACL|NACL]], os usuários não recebem respostas": faltou liberar [[Porta Efemera|portas efêmeras]] na saída (ou entrada).
- "Banco de dados só acessível pela camada de aplicação": [[Security Group|security group]] do banco com a porta do banco e o SG da aplicação como origem.
- "Sem abrir portas de administração": [[Session Manager]].

**Palavras-chave em inglês:** "stateful", "[[Stateless|stateless]]", "[[Porta Efemera|ephemeral ports]]", "inbound rule", "outbound rule", "deny rule", "source [[Security Group|security group]]", "[[Menor Privilegio|least privilege]] network access".

**Pegadinhas clássicas**
- [[Security Group|Security group]] com regra de "deny": não existe.
- [[Network ACL|NACL]] stateful: ela é [[Stateless|stateless]] e exige regra de resposta.
- [[Security Group|Security group]] no nível da [[Sub-rede|sub-rede]] e [[Network ACL|NACL]] no da instância: é o inverso.
- Abrir 22 ou 3389 para `0.0.0.0/0` como "solução": viola [[Menor Privilegio|menor privilégio]]; o enunciado costuma preferir restringir por origem ou usar [[Session Manager]].
- MySQL na 3306 e PostgreSQL na 5432: [[Aurora]] usa a porta do seu engine de compatibilidade.

| Requisito no enunciado | Resposta provável | Por quê |
|---|---|---|
| Bloquear um IP específico | Regra deny em [[Network ACL\|NACL]] | [[Security Group\|Security group]] não tem negar |
| Só a camada web acessa o app | SG do app com origem no SG da web | Referência por SG, sem depender de IPs |
| Respostas bloqueadas após criar [[Network ACL\|NACL]] | Liberar [[Porta Efemera\|portas efêmeras]] | NACL é [[Stateless\|stateless]] |
| Montar [[EFS]] ou volume [[NFS]] | [[TCP]] 2049 | Porta do NFS |
| Montar compartilhamento do [[FSx for Windows File Server\|FSx for Windows]] | [[TCP]] 445 | Porta do [[SMB]] |
| Acesso administrativo sem abrir portas | [[Session Manager]] | Sem exposição de 22 ou 3389 |

## Resumo

> [!abstract] A aula em uma frase
> Firewalls filtram por IP, protocolo e porta: o [[Security Group|security group]] é stateful, atua no recurso e só permite; a [[Network ACL|network ACL]] é [[Stateless|stateless]], atua na [[Sub-rede|sub-rede]], permite e nega em ordem, e por isso exige liberar as [[Porta Efemera|portas efêmeras]] da resposta.

**A lógica, em 6 passos**
1. Uma conexão liga [[Porta Efemera|porta efêmera]] do cliente a porta conhecida do servidor.
2. [[Stateful e Stateless (Firewall)|Firewall stateful]] guarda o estado da conexão e libera a resposta automaticamente.
3. [[Stateful e Stateless (Firewall)|Firewall stateless]] trata cada pacote sozinho: a resposta precisa de regra própria.
4. [[Security Group|Security group]]: stateful, no recurso, só allow, todas as regras valem.
5. [[Network ACL|NACL]]: [[Stateless|stateless]], na [[Sub-rede|sub-rede]], allow e deny, primeira regra que casa vence, `*` nega o resto.
6. Para a [[Network ACL|NACL]], libere ida e volta, incluindo a faixa efêmera do tipo de cliente.

**Números para lembrar**

| O quê | Valor | Por que importa |
|---|---|---|
| Portas | 22, 80, 443, 3389, 3306, 5432, 1433, 1521, 6379, 11211, 2049, 445, 53 | Mapeiam serviço para regra |
| [[IPsec]] e [[BGP]] | [[UDP]] 500 e 4500; [[TCP]] 179 | Conectividade híbrida |
| Faixa efêmera segura | 1024 a 65535 | Cobre qualquer cliente |
| Regras de [[Network ACL\|NACL]] | números de 1 a 32766 | Menor número é avaliado primeiro |

**Tabela-síntese**

Em uma linha: SG é stateful, no recurso, só permite; [[Network ACL|NACL]] é [[Stateless|stateless]], na [[Sub-rede|sub-rede]], permite e nega (tabela completa no corpo da aula). O SG `default` permite tudo entre membros do próprio SG.

**Na prática, isso significa**
- Use [[Security Group|security groups]] por camada, referenciando outros SGs como origem.
- Use [[Network ACL|NACL]] só quando precisar negar explicitamente ou ter uma barreira extra de [[Sub-rede|sub-rede]].
- Ao mexer em [[Network ACL|NACL]], escreva as regras de ida e de volta e teste.

> [!tip] Liga com
> Vem da [[03.04 - Roteamento NAT e Tabelas de Rotas|aula 3.4]] (rotas e [[NAT]]). Segue para a [[03.06 - DNS e Resolucao de Nomes|aula 3.6]] ([[DNS]] na porta 53) e para o [[06 - VPC a Fundo|Módulo 6]] (padrões de SG e [[Network ACL|NACL]] por camada).

## Erros comuns

- **Tentar escrever regra de deny em [[Security Group|security group]].** Não existe; use [[Network ACL|NACL]].
- **Esquecer as [[Porta Efemera|portas efêmeras]] na [[Network ACL|NACL]].** É a causa número um de "as requisições chegam e nenhuma resposta volta".
- **Abrir banco de dados para `0.0.0.0/0`.** A origem correta é o SG da aplicação.
- **Pensar que a [[Network ACL|NACL]] se aplica a tráfego dentro da mesma [[Sub-rede|sub-rede]].** Só vale na fronteira da sub-rede.
- **Esquecer que [[IPv4]] e [[IPv6]] têm regras separadas.** Em [[Dual-Stack|dual-stack]], duplique para `::/0`.

## Pratique

**1.** Uma [[Sub-rede Publica|sub-rede pública]] tem uma [[Network ACL|NACL]] personalizada que permite entrada [[TCP]] 443 e saída TCP 443. Os usuários não conseguem carregar o site. Qual é a correção?

- [ ] a) Permitir saída TCP 1024-65535 na NACL
- [ ] b) Permitir na NACL a saída apenas para as portas 1024 a 5000, a faixa efêmera típica dos navegadores
- [ ] c) Adicionar uma regra de saída para a porta 443 no security group da instância web
- [ ] d) Permitir também a entrada UDP 443 na NACL, para o tráfego HTTP/3

**2.** Uma API precisa acessar um banco [[RDS]] PostgreSQL, e o banco só deve aceitar conexões da camada de aplicação. Qual configuração do [[Security Group|security group]] do banco atende?

- [ ] a) TCP 3306 com origem 0.0.0.0/0
- [ ] b) TCP 5432 com origem 0.0.0.0/0
- [ ] c) TCP 5432 com origem no security group da aplicação
- [ ] d) TCP 1433 com origem no security group da aplicação

**3.** Uma equipe precisa bloquear um endereço IP específico que está atacando a aplicação, mantendo o resto do tráfego liberado. O que usar?

- [ ] a) Criar uma regra de negar para o IP em um security group associado às instâncias web
- [ ] b) Regra de negar em uma network ACL com número menor que as regras de permitir
- [ ] c) Uma rota estática para o IP com alvo blackhole na route table da sub-rede
- [ ] d) Remover a regra de entrada do security group e recriá-la sem o IP atacante

**4.** Um engenheiro removeu todas as regras de saída do [[Security Group|security group]] de um servidor web que aceita [[TCP]] 443 de qualquer origem, esperando derrubar o site, mas os clientes continuam acessando normalmente. Por quê?

- [ ] a) A NACL da sub-rede libera as respostas, e o security group é ignorado quando há NACL
- [ ] b) As regras de saída só são avaliadas para tráfego UDP, nunca para TCP
- [ ] c) O security group recria sozinho a regra de saída padrão a cada nova conexão
- [ ] d) O security group é stateful, então a resposta à conexão permitida na entrada sai sem regra

**5.** A empresa precisa permitir SSH nas instâncias Linux apenas a partir da faixa corporativa 203.0.113.0/24. Qual regra atende?

### Laboratório (opcional): ver portas e estado no seu computador

> [!warning] Sem conta AWS
> Roda só local, sem custo.

1. No Linux ou macOS, rode `ss -tnp` (ou `netstat -ano` no Windows) enquanto navega: cada conexão mostra a porta de origem **alta** (efêmera) e a de destino conhecida (443).
2. Rode `ss -tlnp` (ou `netstat -ano | findstr LISTENING`) para ver as portas em que o seu computador **escuta**.
3. No Linux, `cat /proc/sys/net/ipv4/ip_local_port_range` mostra a faixa efêmera do kernel (em muitos casos 32768 a 60999). No Windows, `netsh int ipv4 show dynamicport tcp` mostra a faixa dinâmica.
