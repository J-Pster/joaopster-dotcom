# Aula 16.7: API Gateway, segurança, throttling, cache e CORS

[[16 - Serverless Lambda e API Gateway|Voltar ao módulo]]

> [!question] Pergunta que esta aula responde
> Quem pode chamar a API ([[IAM]], [[Cognito]], [[Lambda Authorizer|Lambda authorizer]] ou [[JWT]]), como limitar quanto cada cliente chama, como aliviar o backend com cache, por que o navegador bloqueia chamadas "cross-origin" e como separar ambientes com stages?

## O problema: uma API pública é um alvo

Publicar uma API é abrir uma porta na internet. Quatro perguntas aparecem logo: **quem** é o chamador e o que ele pode fazer; **quanto** ele pode chamar sem derrubar o backend; **quantas vezes** a mesma resposta precisa ser recalculada; e **como** um navegador em outro domínio é autorizado a falar com ela. O [[API Gateway]] responde às quatro com recursos próprios, e cada uma vira pergunta de prova.

## Autenticação e autorização

Dois verbos que a prova mistura: **autenticar** é provar quem você é; **autorizar** é decidir o que você pode fazer (Módulo 4). O [[API Gateway]] oferece vários mecanismos, e cada um serve a um tipo de chamador.

| Mecanismo | Quem é o chamador | Como funciona | REST | [[HTTP]] |
|---|---|---|---|---|
| **[[IAM]]** ([[SigV4]]) | Usuários e serviços com credenciais AWS (outras contas, aplicações com [[IAM Role]]) | A requisição é assinada com SigV4 e avaliada por uma [[IAM Policy]] com a ação `execute-api:Invoke` | Sim | Sim |
| **[[Cognito]] user pool** | Usuários finais cadastrados no user pool | O cliente envia o token ([[JWT]]) do [[User Pool]]; o [[API Gateway]] valida | Sim (authorizer do Cognito ou JWT) | Sim (JWT) |
| **[[JWT]] authorizer** | Usuários autenticados por qualquer provedor [[OIDC]]/OAuth 2.0 (inclusive [[Cognito]]) | O [[API Gateway]] valida o token sem escrever função | Sim | Sim |
| **[[Lambda Authorizer]]** | Qualquer esquema customizado ([[OAuth 2.0\|OAuth]] próprio, [[SAML]], tokens legados, cabeçalhos especiais) | Uma função recebe o token ou os parâmetros e devolve uma **política [[IAM]]** | Sim | Sim |
| **[[Resource-Based Policy\|Resource policy]]** | Origens por IP, [[VPC Endpoint\|VPC endpoint]] ou conta | Política JSON na própria API | Sim | Não |
| **[[mTLS]]** | Clientes com certificado | Autenticação mútua [[TLS]] no domínio customizado | Sim | Sim |

(Valores de suporte verificados em novembro de 2026 na tabela oficial "Choose between REST APIs and [[HTTP]] APIs".)

### Lambda authorizer

O **[[Lambda Authorizer|Lambda authorizer]]** (antigo *custom authorizer*) recebe a identidade do chamador, autentica de alguma forma (consultar um provedor [[OAuth 2.0|OAuth]], validar assinatura de token, procurar em um banco) e **devolve uma política [[IAM]]** mais um identificador de principal. O [[API Gateway]] avalia a política: se negar, devolve `403 ACCESS_DENIED`; se permitir, invoca o backend. Existem dois tipos:

- **`TOKEN`:** recebe um token de portador ([[JWT]], [[OAuth 2.0|OAuth]]) de **um** cabeçalho. Permite uma expressão regular para validar o formato antes de chamar a função.
- **`REQUEST`:** recebe cabeçalhos, parâmetros de query, variáveis de stage e de contexto; permite políticas finas e **várias** [[Identity Source|fontes de identidade]]. A documentação recomenda o tipo `REQUEST`.

Com **cache de autorização** ligado, o [[API Gateway]] guarda a política e não chama a função de novo para a mesma identidade durante o [[TTL]], reduzindo [[Latencia|latência]] e custo. Cuidado: a política em cache precisa servir para todos os recursos e métodos da API.

> [!tip] Macete para a prova
> "Users authenticate with **[[Cognito|Amazon Cognito]]**" puxa **Cognito [[User Pool|user pool]] authorizer** (REST) ou **[[JWT]] authorizer** ([[HTTP]]). "Third-party [[Identity Provider|identity provider]] / custom token validation logic / [[SAML]]" puxa **[[Lambda Authorizer|Lambda authorizer]]**. "Other [[Conta AWS|AWS accounts]] or applications with [[IAM Role|IAM roles]] call the API" puxa **[[IAM]] authorization**. "Allow only a specific IP range or [[VPC]]" puxa **[[Resource-Based Policy|resource policy]]** (REST).

> [!example] Exemplo: três chamadores, três mecanismos
> O app móvel autentica usuários no [[Cognito]] e envia o [[JWT]]: **Cognito authorizer**. O backend interno de outra conta da empresa chama a API com uma role: **[[IAM]]**. Um parceiro usa tokens emitidos pelo próprio sistema legado dele: **[[Lambda Authorizer|Lambda authorizer]]** que valida o token e devolve a política.

### API key não é autenticação

Uma **API key** é uma string alfanumérica de 20 a 128 caracteres que identifica um cliente para um **[[Usage Plan|usage plan]]**. Ela serve para **medir e limitar**, não para provar identidade: a chave vai em cabeçalho, pode vazar e não carrega permissões. A documentação manda usá-la **em conjunto** com um [[Lambda Authorizer|Lambda authorizer]], [[IAM]] ou [[Cognito]] para controlar o acesso. É uma das pegadinhas mais clássicas de prova.

### Proteção na borda

- **[[WAF]]**: só em REST APIs (não em [[HTTP]] APIs). Bloqueia [[SQL Injection|SQL injection]], [[Cross-Site Scripting|XSS]], IPs maliciosos e aplica regras de taxa por IP ([[19 - Seguranca de Aplicacoes e Deteccao de Ameacas|Módulo 19]]). Nuance: o WAF não se associa diretamente a uma HTTP API; a alternativa é pôr um [[CloudFront]] com WAF na frente ([[18 - Borda e DNS CloudFront Global Accelerator e Route 53|Módulo 18]]). Na prova, se o enunciado exige WAF diretamente no [[API Gateway]], a resposta é REST.
- **Private API**: nunca exposta à internet (Aula 16.6).
- **[[TLS]]** com certificado do [[ACM]] no domínio customizado (Módulo 8).

## Throttling: proteger o backend e dividir a capacidade

O [[API Gateway]] limita requisições com o algoritmo **[[Token Bucket|token bucket]]**: o balde recebe tokens a uma taxa constante (requisições por segundo) até um tamanho máximo (burst); cada requisição consome um token; se o balde esvazia, a requisição recebe **`429 Too Many Requests`**. Os limites se aplicam em camadas, na ordem que a documentação descreve (verificado em novembro de 2026):

1. **Por cliente ou por método**, definido em um **[[Usage Plan|usage plan]]** (identifica o cliente pela API key).
2. **Por método em um stage.**
3. **Por conta e Região:** 10.000 requisições por segundo, com burst de 5.000 (valores padrão; 2.500 e 1.250 em algumas [[Regiao AWS|Regiões]]; aumentável).
4. **Limite regional da AWS**, que o cliente não controla.

Os limites mais específicos não podem ultrapassar os mais gerais, e todos são **melhor esforço**: a documentação diz para pensá-los como alvos, não como tetos garantidos, e **não usá-los para controlar custos nem bloquear acesso**. Para custo use [[Budgets]]; para abuso use [[WAF]] com regras baseadas em taxa.

### Usage plans

Um **[[Usage Plan|usage plan]]** define quem pode acessar quais stages e métodos (via API keys) e aplica **[[Throttling|throttling]]** (taxa e burst) e **quota** (máximo de requisições em um período, como 100 mil por mês). Uma chave pode estar em mais de um plano, mas só em um plano por stage. É a ferramenta para vender uma API por camadas (gratuito, pago, empresarial). Só existe em REST APIs.

> [!example] Exemplo: planos Bronze e Ouro
> Plano Bronze: 10 requisições por segundo, burst 20, quota de 10.000 por dia. Plano Ouro: 200 por segundo, burst 400, quota de 1 milhão por dia. Cada parceiro recebe uma chave associada ao plano contratado. Um parceiro Bronze que passa do limite recebe 429 sem afetar os demais.

> [!info] Ligando os pontos
> O limite de 10.000 requisições por segundo do [[API Gateway]] versus 1.000 de concorrência do [[Lambda]] (Aula 16.3) explica por que cargas altas pedem aumento de concorrência, ou uma fila entre os dois. O [[Throttling|throttling]] do API Gateway protege o backend do excesso de chamadas, mas **não** garante que o Lambda aguente o que passar.

## Cache de respostas

O [[API Gateway]] pode **guardar as respostas** do backend por um tempo, servindo requisições repetidas sem chamar o Lambda. Isso reduz [[Latencia|latência]], carga e custo (verificado em novembro de 2026):

- Disponível em **REST APIs**, ativado **por stage**, com capacidade escolhida (maior capacidade, mais desempenho e custo).
- **[[TTL]] padrão de 300 segundos**; máximo de **3.600**; TTL 0 desativa.
- Por padrão só métodos **GET** são cacheados; outros métodos exigem configuração específica.
- Resposta cacheável de até **1 MB** (1.048.576 bytes).
- É **cobrado por hora** conforme o tamanho; **não** entra na camada gratuita. Ativar leva até 4 minutos, e mudar a capacidade **apaga** o cache existente.
- É *best effort*: acompanhe `CacheHitCount` e `CacheMissCount` no [[CloudWatch]].
- **[[Cache Key|Chave de cache]]:** por padrão a chave é o recurso e o método; você pode incluir **parâmetros de query, de caminho ou cabeçalhos** como parte da chave, e cada combinação distinta vira uma entrada separada. Resposta que varia por usuário (por exemplo, por `Authorization`) exige incluir esse cabeçalho como chave de cache; sem isso, um usuário pode receber a resposta de outro.
- **[[Invalidacao de Cache|Invalidação]] pelo cliente:** o cliente pode forçar o refresh de uma entrada enviando o cabeçalho `Cache-Control: max-age=0`, e isso exige a permissão [[IAM]] `execute-api:InvalidateCache` (ou a API pode ser configurada para aceitar sem autorização, o que não é recomendado).
- **Flush do stage:** o cache inteiro do stage pode ser esvaziado de uma vez (flush), por exemplo depois de uma correção de dados.

Onde cachear (visão de camadas, que o Módulo 14 detalhou): [[CloudFront]] na borda (conteúdo estático e respostas públicas), cache do [[API Gateway]] (respostas da API), [[ElastiCache]] ou [[DAX]] no acesso a dados. O enunciado indica a camada pelo requisito: "reduce calls to the backend Lambda" aponta o cache do API Gateway; "reduce reads on [[DynamoDB]]" aponta DAX.

> [!example] Exemplo: catálogo de produtos
> `GET /produtos` devolve o mesmo JSON para todos, e o catálogo muda poucas vezes por dia. Com cache de 600 segundos no stage `prod`, 99% das chamadas são respondidas pelo cache e o Lambda roda só uma vez a cada 10 minutos por variação de parâmetros.

## CORS: o navegador também protege

Um navegador bloqueia por padrão a página `https://app.exemplo.com` de ler respostas de `https://api.exemplo.com`, porque a origem (domínio, subdomínio, porta ou protocolo) é diferente. É a **política de mesma origem**. O **[[CORS]]** (*cross-origin resource sharing*) é o mecanismo pelo qual o **servidor** diz ao navegador quais origens, métodos e cabeçalhos são permitidos. O sintoma clássico é `Cross-Origin Request Blocked` no console do navegador, com a API funcionando perfeitamente via `curl`.

Como funciona (verificado em novembro de 2026):

- **Requisição simples** (GET, HEAD ou POST com tipos de conteúdo básicos e sem cabeçalhos customizados): a resposta precisa incluir `Access-Control-Allow-Origin` (com `*` ou a origem).
- **Requisição não simples** (por exemplo `PUT`, `DELETE` ou cabeçalho `Authorization`): o navegador envia antes uma **preflight**, uma requisição `OPTIONS`, e só envia a real se a resposta autorizar com `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods` e `Access-Control-Allow-Headers`.
- **REST API com integração não proxy:** você cria um método `OPTIONS` com integração **MOCK** que devolve esses cabeçalhos.
- **REST API com Lambda proxy:** configure o método `OPTIONS` (por exemplo, um MOCK criado pela opção "Enable [[CORS]]" do console, ou tratado pela própria função) para responder ao **preflight**, **e** faça a função devolver `Access-Control-Allow-Origin` em toda **resposta real**, porque no proxy o [[API Gateway]] não injeta esses cabeçalhos nas respostas do backend.
- **[[HTTP]] API:** há configuração de [[CORS]] pronta no recurso, que trata o preflight.

> [!warning] CORS não é segurança de servidor
> [[CORS]] só instrui **navegadores**. Não impede `curl`, scripts ou outros servidores de chamar a API. A proteção real continua sendo autenticação, autorização e [[WAF]].

## Stages, deployments e canary

Uma API REST só vira acessível depois de um **deployment** em um **stage**. Cada stage tem sua URL, variáveis de stage, [[Throttling|throttling]], cache, logs e configurações próprias, o que separa `dev`, `homolog` e `prod` sem duplicar a API. Pontos que caem:

- Variáveis de stage permitem apontar o mesmo stage para o [[Lambda Alias|alias do Lambda]] correspondente (`dev` para o alias `dev`).
- **[[Canary Deployment|Canary release]]** (só REST): o stage envia uma porcentagem do tráfego para o deployment novo e o resto para o antigo; se estiver bom, promove; se não, desfaz. É o equivalente, na API, do alias ponderado do Lambda (Aula 16.5).
- [[HTTP]] APIs têm deploy automático por stage.
- A criação de deployments é limitada (1 a cada 5 segundos por conta).

### Observabilidade

[[CloudWatch]] métricas (contagem, erros 4XX e 5XX, [[Latencia|latência]] e latência da integração, acertos e falhas de cache), logs de acesso, logs de execução (REST) e [[X-Ray]] (REST). Os eventos de log do [[API Gateway]] são truncados em 1.024 bytes; corpos grandes de requisição e resposta não aparecem inteiros. Para diagnosticar pelo código (401, 403, 429, 502, 504), veja a tabela da [[16.06 - API Gateway Tipos Endpoints e Integracoes|Aula 16.6]].

Cobertura: **Task 1.2** (proteção na borda e autorização), **Task 2.1** (APIs escaláveis, [[Throttling|throttling]]) e **Task 3.2** (cache para desempenho).

**Palavras-chave em inglês:**
- "Authenticate users with [[Cognito|Amazon Cognito]]" puxa **Cognito authorizer / [[JWT]] authorizer**.
- "Custom authentication logic", "validate third-party tokens" puxam **[[Lambda Authorizer|Lambda authorizer]]**.
- "Limit each customer to N requests per second / monthly quota" puxa **usage plans**.
- "Reduce [[Latencia|latency]] and load on the backend for repeated GET requests" puxa **cache do [[API Gateway]]**.
- "[[CORS]] error in the browser" puxa **habilitar CORS** (OPTIONS ou resposta da função).
- "Gradually release a new API version" puxa **[[Canary Deployment|canary deployment]] do stage**.
- "Protect the API from [[SQL Injection|SQL injection]] / bots" puxa **[[WAF]]** (e portanto REST).

**Pegadinhas clássicas:**
- API key não autentica; combine com authorizer.
- [[Throttling]] e quotas são melhor esforço; não controlam custo.
- [[WAF]] não se associa a [[HTTP]] API.
- [[CORS]] é regra do navegador; não protege contra chamadas fora do navegador.
- Com Lambda proxy, os cabeçalhos [[CORS]] vêm da função, não do [[API Gateway]].
- O cache é cobrado por hora e fica por stage.

| Requisito no enunciado | Resposta provável | Por quê |
|---|---|---|
| Usuários do app autenticam no [[Cognito]] | Cognito [[User Pool\|user pool]] authorizer (REST) ou [[JWT]] authorizer ([[HTTP]]) | Valida o token sem código |
| Validar tokens de [[Identity Provider\|IdP]] próprio com lógica customizada | [[Lambda Authorizer\|Lambda authorizer]] | Devolve uma política [[IAM]] |
| Outra [[Conta AWS\|conta AWS]] chama a API com role | [[IAM]] authorization | Assinatura [[SigV4]] e policy |
| Parceiros com cotas diferentes por plano | Usage plans e API keys | [[Throttling]] e quota por cliente |
| Mesmo GET repetido sobrecarrega o backend | [[Cache]] no stage da REST | Responde sem invocar o Lambda |
| Navegador bloqueia por origem diferente | [[CORS]] na API ou na função | Autoriza a origem |
| Liberar nova versão da API para 5% dos usuários | Canary no stage | Divide tráfego entre deployments |

## Resumo

> [!abstract] A aula em uma frase
> A API é protegida por autorização ([[IAM]], [[Cognito]]/JWT, [[Lambda Authorizer|Lambda authorizer]]), limitada por usage plans e [[Throttling|throttling]], acelerada por cache de stage e liberada para navegadores por [[CORS]], e cada recurso responde a uma palavra-chave diferente da prova.

**A lógica, em 5 passos**
1. Identifique o chamador e escolha o mecanismo: [[IAM]], [[Cognito]]/JWT, [[Lambda Authorizer|Lambda authorizer]].
2. Use API key só para medição, nunca como autenticação.
3. Limite por cliente com usage plans e proteja a conta com [[Throttling|throttling]]; conte com melhor esforço.
4. Cacheie GETs repetidos no stage para poupar o backend.
5. Habilite [[CORS]] para navegadores e use stages e canary para separar e liberar versões.

**Números para lembrar**

| O quê | Valor | Por que importa |
|---|---|---|
| Limite de conta | 10.000 RPS, burst 5.000 | Teto padrão compartilhado por todas as APIs |
| [[TTL de Cache\|TTL do cache]] | padrão 300 s, máximo 3.600 s | [[TTL]] 0 desliga |
| Resposta cacheável | até 1 MB | Respostas maiores não entram |
| [[Usage Plan\|Chave de API]] | 20 a 128 caracteres | Identifica, não autentica |
| Autorizadores por API | 10 (Lambda e [[Cognito]]) | Limite aumentável por suporte |
| Log do [[API Gateway]] | 1.024 bytes por evento | Corpo grande aparece truncado |

**Na prática, isso significa**
- Para [[Cognito]], prefira o authorizer nativo ao [[Lambda Authorizer|Lambda authorizer]].
- Cota por cliente exige REST e usage plans.
- [[Cache]] só em REST e custa por hora.
- Para [[WAF]] ou chave, não escolha [[HTTP]] API.

## Erros comuns

- Tratar API key como senha.
- Esperar que [[Usage Plan|usage plan]] seja um teto rígido de custo.
- Esquecer que [[WAF]] não se associa diretamente a [[HTTP]] API (a alternativa é [[CloudFront]] com WAF na frente).
- Confundir o erro de [[CORS]] com falha de autenticação (a chamada via curl funciona).
- Habilitar cache sem notar o custo por hora e sem considerar GETs com dados por usuário.
- Cachear um GET com dados por usuário sem incluir `Authorization` (ou outro identificador) na [[Cache Key|chave de cache]], entregando a resposta de um usuário a outro.
- Colocar a política em cache do authorizer válida só para um recurso e liberar a API inteira por engano.

## Pratique

**1.** Uma API REST é consumida por um app móvel cujos usuários se cadastram em um [[Cognito]] [[User Pool|user pool]]. A equipe quer autenticar sem escrever código. O que usar?

- [ ] a) Lambda authorizer com validação manual do token no código.
- [ ] b) API keys distribuídas individualmente a cada usuário do app.
- [ ] c) Cognito user pool authorizer (ou JWT authorizer).
- [ ] d) Resource policy liberando o IP dos usuários do aplicativo móvel.

**2.** Um parceiro usa tokens emitidos por um sistema de identidade proprietário, com regras de validação próprias. Qual mecanismo atende?

- [ ] a) Lambda authorizer que valida o token e devolve a política.
- [ ] b) Cognito user pool authorizer sem nenhuma alteração na configuração.
- [ ] c) API key associada a um usage plan para cada parceiro integrado.
- [ ] d) Integração MOCK com validação do token feita pelo próprio stage.

**3.** Uma API vende acesso por planos: gratuito com 1.000 chamadas por dia e pago com 1 milhão. O que configurar?

- [ ] a) Dois stages com cache de tamanhos diferentes.
- [ ] b) Duas contas AWS com limites de Lambda diferentes.
- [ ] c) AWS WAF com regra por país.
- [ ] d) Usage plans com API keys e quotas por plano.

**4.** O time acredita que uma API key protege a API contra acesso não autorizado. Qual é a correção?

- [ ] a) Está correto: a chave é a forma recomendada pela AWS de autenticar chamadores.
- [ ] b) A chave só identifica o cliente; autentique com IAM, Cognito ou authorizer.
- [ ] c) API keys são criptografadas com KMS e por isso são seguras para autenticar.
- [ ] d) API keys só funcionam em HTTP APIs e nunca em REST APIs.

**5.** Quais DUAS afirmações sobre [[Throttling|throttling]] e quotas do [[API Gateway]] estão corretas? (Escolha DUAS.)

- [ ] a) São garantias rígidas que impedem qualquer excesso.
- [ ] b) Aplicam-se em camadas, de cliente ou método até o limite regional.
- [ ] c) Servem como mecanismo confiável de controle de custos.
- [ ] d) O limite padrão de conta é de 10.000 RPS, com burst de 5.000.
- [ ] e) Só existem em WebSocket APIs.

**6.** Uma API GET devolve um catálogo que muda poucas vezes ao dia e sobrecarrega o backend. Qual configuração reduz as chamadas ao Lambda?

- [ ] a) Cache no stage da REST API, com TTL adequado.
- [ ] b) Aumentar a concorrência provisionada do Lambda.
- [ ] c) Habilitar o AWS WAF na API.
- [ ] d) Trocar a REST por uma HTTP API com cache automático.

**7.** Qual afirmação sobre o cache do [[API Gateway]] é correta?

- [ ] a) É gratuito e ativado por padrão em todos os stages.
- [ ] b) Funciona nas HTTP APIs com TTL de até 24 horas.
- [ ] c) Armazena respostas de até 10 MB.
- [ ] d) É cobrado por hora, por tamanho, e o TTL padrão é de 300 segundos.

**8.** O navegador mostra "Cross-Origin Request Blocked" ao chamar uma API REST com Lambda proxy; `curl` funciona. Qual a causa e a correção?

- [ ] a) A API está fora do ar; reiniciar o stage e fazer novo deployment.
- [ ] b) Faltam cabeçalhos CORS; a função deve devolver Access-Control-Allow-Origin.
- [ ] c) O certificado do ACM expirou; é preciso renová-lo no domínio customizado.
- [ ] d) O usage plan expirou; aumentar a quota mensal do plano de cada cliente.

**9.** Uma empresa quer liberar uma nova versão de uma REST API para 10% dos clientes antes de promover. Qual recurso usar?

- [ ] a) Reduzir o throttling do stage a 10%.
- [ ] b) Dois domínios customizados, um por versão, sem automação.
- [ ] c) Um segundo usage plan com quota equivalente a 10% da quota atual.
- [ ] d) Canary release no stage.

**10.** Uma API REST pública sofre tentativas de [[SQL Injection|SQL injection]] e abuso por IP. Quais DUAS medidas ajudam? (Escolha DUAS.)

- [ ] a) Associar um AWS WAF com regras gerenciadas e regra baseada em taxa.
- [ ] b) Trocar para HTTP API para ganhar proteção embutida.
- [ ] c) Usar autenticação adequada, como Cognito ou IAM, nas rotas.
- [ ] d) Aumentar o TTL do cache para 1 hora.
- [ ] e) Distribuir API keys a todos os usuários anônimos.

**11.** Qual descrição de um [[Lambda Authorizer|Lambda authorizer]] está correta?

- [ ] a) Retorna uma política IAM, que o API Gateway avalia.
- [ ] b) Substitui a execution role da função de backend da API.
- [ ] c) Só aceita tokens emitidos pelo Cognito user pool da conta.
- [ ] d) Executa depois do backend para filtrar o conteúdo da resposta.

**12.** Um app web em `app.exemplo.com` chama uma [[HTTP]] API em `api.exemplo.com` e o navegador bloqueia a chamada. Qual é a solução MAIS direta?

- [ ] a) Migrar para REST API edge-optimized.
- [ ] b) Configurar CORS na HTTP API, permitindo a origem do app.
- [ ] c) Habilitar o cache no stage.
- [ ] d) Criar uma VPN entre os dois domínios.

> [!success]- Gabarito
> **1. c)** o authorizer nativo valida o token do [[User Pool|user pool]] sem código; a exige função e manutenção; b não autentica pessoas; d não identifica usuários móveis.
> **2. a)** o [[Lambda Authorizer|Lambda authorizer]] aceita lógica customizada e devolve a política; b só entende tokens do [[Cognito]]; c só mede; d não autoriza ninguém.
> **3. d)** usage plans com API keys aplicam quota e [[Throttling|throttling]] por plano; a e b não medem por cliente; c filtra por país, não por plano.
> **4. b)** a chave identifica o cliente para limites, não prova identidade; a erra; c inventa uma proteção que não existe; d é falso, pois a chave é de REST.
> **5. b) e d)** os limites se aplicam em camadas e o padrão da conta é 10.000 RPS, burst 5.000; a e c erram porque são melhor esforço; e é falso.
> **6. a)** cache de stage serve a resposta sem invocar o Lambda; b melhora [[Latencia|latência]] mas não reduz chamadas; c filtra ataques; d erra porque a [[HTTP]] API não tem cache.
> **7. d)** cobra por hora e o [[TTL]] padrão é 300 s; a erra, pois não é gratuito; b erra, [[HTTP]] API não tem cache; c erra, o limite é 1 MB.
> **8. b)** em Lambda proxy a função deve devolver `Access-Control-Allow-Origin` na resposta real (e, se a chamada for não simples, o preflight OPTIONS também precisa ser respondido); a, c e d são causas que não explicam bloqueio só no navegador.
> **9. d)** canary no stage envia uma fração do tráfego ao deployment novo; a limita taxa; b dividiria clientes manualmente; c limita o consumo de um grupo de clientes, não divide versões da API.
> **10. a) e c)** [[WAF]] trata injeção e abuso e a autenticação reduz a superfície; b erra porque a [[HTTP]] API não suporta WAF; d não ajuda; e não autentica.
> **11. a)** o authorizer devolve uma política [[IAM]] avaliada pelo [[API Gateway]]; b e d erram na função; c erra porque aceita tokens de qualquer origem.
> **12. b)** a [[HTTP]] API tem configuração de [[CORS]] própria; a não resolve a origem; c e d não tratam a política do navegador.
