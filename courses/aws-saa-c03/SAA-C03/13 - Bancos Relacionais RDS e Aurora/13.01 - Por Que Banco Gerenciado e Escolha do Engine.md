# Aula 13.1: Por que banco gerenciado e como escolher o engine

[[13 - Bancos Relacionais RDS e Aurora|Voltar ao módulo]]

> [!question] Pergunta que esta aula responde
> O que a AWS assume quando você usa o [[RDS]] em vez de instalar um banco em uma instância [[EC2]], o que continua sendo seu, e como escolher entre MySQL, PostgreSQL, bancos comerciais e [[Aurora]]?

## O problema: banco de dados dá trabalho que não é o seu produto

Instalar PostgreSQL em uma [[EC2|instância EC2]] leva dez minutos. Operá-lo por cinco anos leva muito mais: aplicar patches do sistema operacional e do engine sem derrubar a aplicação, montar réplica para [[Alta Disponibilidade]], agendar backup e testar o restore, dimensionar disco antes de ele encher, monitorar, trocar hardware que falha. Nenhuma dessas tarefas é diferencial do seu negócio, e todas têm um ponto em comum: se você errar, o banco cai e leva a aplicação junto.

O **[[RDS|Amazon RDS]]** (Relational Database Service) é o serviço que assume essas tarefas. A documentação resume a divisão de responsabilidades em uma tabela (verificado em novembro de 2026):

| Tarefa | Datacenter próprio | Banco em [[EC2]] | [[RDS]] |
|---|---|---|---|
| Otimização da aplicação (queries, índices, modelo) | Você | Você | **Você** |
| Escalabilidade | Você | Você | AWS |
| [[Alta Disponibilidade\|Alta disponibilidade]] | Você | Você | AWS |
| Backups do banco | Você | Você | AWS |
| Patch do software do banco e instalação | Você | Você | AWS |
| Patch e instalação do sistema operacional | Você | Você | AWS |
| Manutenção de servidor, ciclo de vida do hardware, energia, rede e refrigeração | Você | AWS (hardware) | AWS |

A primeira linha é a que cai na prova e a que mais pega desenvolvedores: **ajustar queries e modelar o banco continua sendo responsabilidade do cliente**. O [[RDS]] não conserta um `SELECT` sem índice. Isso é o [[Modelo de Responsabilidade Compartilhada]] aplicado a banco de dados: a fronteira da AWS sobe até o engine, e a sua começa no schema.

> [!info] Ligando os pontos
> No [[01 - Nuvem e Infraestrutura Global AWS|Módulo 1]] você viu que a linha da [[Modelo de Responsabilidade Compartilhada|responsabilidade compartilhada]] se move conforme o serviço. [[EC2]] é "você cuida do sistema operacional para cima"; [[RDS]] é "a AWS cuida até o engine"; um serviço totalmente [[Serverless|serverless]] como o [[DynamoDB]] (próximo módulo) leva a AWS ainda mais para cima. Quanto mais para cima a linha, menor o [[Overhead Operacional]], que é exatamente o [[Qualificador|qualificador]] que a prova usa.

A própria documentação da AWS recomenda o [[RDS]] como "escolha padrão para a maioria dos deployments relacionais", e a alternativa (banco em [[EC2]]) como a que faz você gastar mais tempo gerenciando software e hardware. Você, que já opera RDS PostgreSQL no dia a dia, conhece o lado prático: o ganho é não ter um [[Runbook|runbook]] de patch e [[Failover|failover]]. O que a prova quer saber é quando a regra tem exceção.

> [!example] Quando o banco em EC2 ainda faz sentido
> Uma empresa precisa de uma extensão de PostgreSQL que o [[RDS]] não oferece, ou de acesso ao sistema operacional para instalar um agente de terceiros ligado ao banco. Aqui há duas saídas antes de abandonar o gerenciado: o [[RDS Custom]] (para Oracle e SQL Server, com acesso ao sistema operacional, explicado mais abaixo, em "RDS Custom em um parágrafo") ou, se nem isso servir, o [[EC2]] com toda a responsabilidade nas suas costas. A prova costuma tratar o EC2 como a **pior** resposta quando o enunciado pede "menor [[Overhead Operacional|overhead operacional]]".

## O que é um RDS por dentro

O bloco básico do [[RDS]] é a **DB instance**: um ambiente de banco isolado que pode conter vários bancos criados por você. Cada DB instance combina:

- **Engine**: o software do banco (MySQL, PostgreSQL etc.) e a versão.
- **[[DB Instance Class|DB instance class]]**: CPU e memória (aula 13.2).
- **Storage**: volumes do [[EBS]] gerenciados pelo [[RDS]] para dados e logs (aula 13.2). Você não vê o volume na lista de volumes EBS da sua conta; ele é do serviço.
- **Endpoint [[DNS]]**: o nome que a aplicação usa. Você nunca conecta em IP, e isso é a base do [[Failover|failover]] (aula 13.3).
- **[[Security Group]]**: controla quem alcança a porta do banco.
- **[[DB Subnet Group|DB subnet group]]**: o conjunto de [[Sub-rede|sub-redes]] da [[VPC]] onde o [[RDS]] pode colocar a instância. A documentação do [[CloudFormation]] exige pelo menos duas sub-redes em duas [[Zona de Disponibilidade|AZs]] diferentes no mesmo [[Regiao AWS|Region]] (verificado em novembro de 2026), e é isso que permite o RDS escolher uma segunda AZ para o standby.
- **[[Parameter Group|Parameter group]]**: os parâmetros de configuração do engine (equivalente ao `postgresql.conf` ou `my.cnf`).

O padrão de arquitetura que a documentação ilustra é o clássico de três camadas: balanceador na frente, servidores de aplicação, e o [[RDS]] em **[[Sub-rede Privada|sub-redes privadas]]**, sem rota da internet para ele. A aplicação, em outra camada, alcança o banco porque o [[Security Group|security group]] do banco aceita o security group da aplicação como origem. Você já faz isso com o seu [[ECS]].

> [!warning] O RDS não dá acesso ao host
> Para entregar a experiência gerenciada, o [[RDS]] não deixa você entrar no servidor por SSH nem executar operações que exigem privilégio de superusuário do sistema operacional. Alguns procedimentos e objetos privilegiados do engine também são restritos. Se um requisito do enunciado disser "acesso ao sistema operacional do banco", o RDS comum está fora.

## Engines: o que existe e como escolher

O [[RDS]] oferece seis engines (verificado em novembro de 2026): **IBM Db2, MariaDB, Microsoft SQL Server, MySQL, Oracle Database e PostgreSQL**. Além deles existe o **[[Aurora|Amazon Aurora]]**, que é um banco relacional compatível com MySQL ou com PostgreSQL, mas com arquitetura própria de armazenamento (aulas 13.7 e 13.8). A página oficial trata o Aurora em um guia separado do RDS "tradicional".

A prova não pede para comparar versões de engine. Ela quer que você escolha pelo **critério de decisão**. Na lista de habilidades da Task 3.3 está literalmente "escolher um engine de banco de dados (MySQL vs PostgreSQL)", e na 4.3 "escolher o engine por custo". As perguntas-guia:

1. **Aplicação já existe?** Se ela fala o dialeto de um engine (T-SQL, PL/SQL, Oracle-specific), o caminho de menor risco é o mesmo engine no [[RDS]]: é uma **[[Migracao Homogenea|migração homogênea]]**. Mudar de engine é uma **[[Migracao Heterogenea|migração heterogênea]]**, que exige converter schema e código (ferramentas [[Schema Conversion Tool]], que converte schema e código, e [[DMS]], que move os dados, Módulo 23).
2. **Quer fugir de licença comercial?** Oracle e SQL Server têm custo de licença. MySQL, MariaDB e PostgreSQL são open source e não têm taxa de licença. Para novos projetos, o argumento de custo puxa para PostgreSQL ou MySQL (ou [[Aurora]] compatível).
3. **Precisa dos recursos de [[Alta Disponibilidade|alta disponibilidade]] e escala mais modernos?** Alguns recursos só existem em certos engines. O [[Multi-AZ DB Cluster]] (um cluster com um writer e dois readers em três [[Zona de Disponibilidade|AZs]], aula 13.3) existe apenas para [[RDS]] for MySQL e RDS for PostgreSQL; ele não está disponível para Db2, MariaDB, Oracle nem SQL Server. O [[RDS Proxy]] (um intermediário que mantém um [[Pool de Conexoes|pool de conexões]] na frente do banco, aula 13.6) tem páginas de limitações para MariaDB, SQL Server, MySQL e PostgreSQL. A [[IAM Database Authentication|autenticação IAM de banco]] (entrar no banco com um token temporário no lugar de senha, aula 13.5) funciona com MariaDB, MySQL e PostgreSQL.
4. **Precisa de performance e escala de leitura além do [[RDS]] padrão, ou resiliência entre [[Regiao AWS|Regiões]] com [[RPO]] de segundos?** Aí a resposta tende a ser [[Aurora]].

### MySQL ou PostgreSQL?

Para a prova, a escolha entre os dois raramente é técnica profunda; é de **compatibilidade** com o que a empresa já usa e de **recursos de ecossistema**. Duas diferenças que ajudam a responder: o [[Aurora]] MySQL oferece o recurso de [[Backtrack]] e o Aurora PostgreSQL não (aula 13.8); e o PostgreSQL é o engine em que a AWS documenta controle de [[RPO]] do Global Database (`rds.global_db_rpo`). Fora isso, trate os dois como equivalentes e use a pista do enunciado ("a aplicação usa PostgreSQL").

### Bancos comerciais e licenças

Verificado em novembro de 2026 nas páginas de licenciamento do [[RDS]]:

- **[[RDS]] for Oracle**: o modelo **License Included (LI)** existe só para a edição **Standard Edition Two (SE2)**; para Enterprise Edition e SE2 existe o modelo **[[BYOL|Bring Your Own License]] (BYOL)**, em que você leva a licença que já tem.
- **[[RDS]] for SQL Server**: o modelo **License Included** cobre as edições Enterprise, Standard, Web e Express. Para levar licença própria, a documentação atual descreve **Bring Your Own Media (BYOM)**, com direitos de License Mobility via Software Assurance. Questões de simulado antigas falam em "[[BYOL]]" para SQL Server; é o mesmo espírito.

A consequência de custo: no License Included, o preço da licença está embutido na hora da instância. Se a empresa já tem licenças com direito de mobilidade, o [[BYOL]]/BYOM costuma baixar o custo. Em ambos os casos, **[[Reserved DB Instance|reserved DB instances]]** de Oracle License Included e SQL Server não têm flexibilidade de tamanho (aula 13.9).

> [!example] Escolhendo engine em um cenário de prova
> "Uma empresa migra uma aplicação interna que usa Oracle com procedures PL/SQL extensas. Ela quer o MENOR esforço de migração e manter o mesmo código." A resposta é **[[RDS]] for Oracle**: [[Migracao Homogenea|migração homogênea]], sem reescrever PL/SQL. Se o enunciado trocar para "quer reduzir custo de licença e aceita converter o schema", aparecem [[Aurora]] PostgreSQL e as ferramentas do Módulo 23. O [[Qualificador|qualificador]] decide.

## RDS comum, RDS Custom ou Aurora?

| Se o requisito for | Escolha | Por quê |
|---|---|---|
| Banco relacional padrão, menor overhead | **[[RDS]]** | AWS cuida de patch, backup, [[Failover\|failover]] |
| Acesso ao sistema operacional e ao banco para dependências de terceiros (Oracle ou SQL Server) | **[[RDS Custom]]** | Você ganha privilégio de administrador, com automação parcial |
| Controle total do host, extensão ou software que nenhum serviço gerenciado aceita | **Banco em [[EC2]]** | Você assume tudo |
| Alta performance, 15 [[Read Replica\|réplicas de leitura]], [[Failover\|failover]] em segundos, Global Database, [[Serverless\|serverless]] | **[[Aurora]]** | Armazenamento compartilhado distribuído |

### RDS Custom em um parágrafo

O **[[RDS Custom]]** existe para os engines **Oracle e SQL Server**, nos casos em que uma aplicação empacotada (ERP, sistema legado de terceiros) exige acesso ao sistema operacional e ao banco para instalar agentes, drivers ou configurações que o [[RDS]] comum bloqueia. Você ganha privilégio de administrador no host, e a AWS mantém **automação parcial** (backup, monitoramento e recuperação, conforme a documentação). O preço dessa liberdade é a divisão de responsabilidades: **a personalização passa a ser sua**, e uma mudança que quebre a automação pode tirar a instância do estado suportado. Há limitações: por exemplo, o [[RDS Proxy]] **não funciona com RDS Custom for SQL Server** (página de limitações do RDS Proxy, verificado em novembro de 2026). Em resumo, o RDS Custom fica entre o RDS comum (menos controle, menos trabalho) e o [[EC2]] (controle total, todo o trabalho). Visão geral em [Amazon RDS Custom](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-custom.html).

## Onde o banco relacional entra (e onde não entra)

Um banco relacional é a escolha natural para dados estruturados com relações, transações [[Transacoes ACID|ACID]] (atômicas, consistentes, isoladas e duráveis) e consultas flexíveis por SQL: pedidos, cadastros, financeiro. Duas escolhas que **não** são resolvidas por esta família de serviços:

- **Acesso por chave em escala massiva, [[Latencia|latência]] de milissegundos e esquema flexível**: tende a [[DynamoDB]] ([[14 - DynamoDB Cache e Bancos de Proposito Especifico|Módulo 14]]).
- **Análise de grandes volumes históricos ([[OLAP]])**: tende a [[Redshift]] ou [[Athena]] ([[22 - Dados Analytics e Ingestao|Módulo 22]]). Rodar relatórios pesados direto no banco transacional ([[OLTP]]) disputa recurso com os usuários; a solução tem etapas: [[Read Replica|réplica de leitura]] dedicada (aula 13.4) e, quando o volume pede, um [[Data Warehouse|data warehouse]].

> [!tip] OLTP e OLAP em uma linha
> [[OLTP]]: muitas transações pequenas e rápidas (comprar, cadastrar), é o terreno do [[RDS]] e do [[Aurora]]. [[OLAP]]: poucas consultas enormes que varrem milhões de linhas (relatório trimestral), é o terreno do [[Redshift]].

## Como um banco relacional escala (a pergunta que organiza o módulo)

Todo o módulo gira em torno de quatro eixos. Guarde esta tabela, porque a prova quase sempre cai em um deles:

| Eixo | Problema | Ferramenta | Aula |
|---|---|---|---|
| [[Disponibilidade]] | A [[Zona de Disponibilidade\|AZ]] do banco falha | [[Multi-AZ]] (instância ou cluster), [[Aurora Replica\|réplicas do Aurora]] | 13.3, 13.7 |
| Escala de **leitura** | Muitas consultas SELECT | [[Read Replica]], [[Aurora Replica\|réplicas do Aurora]], [[Cache]] | 13.4, 13.7 |
| Escala de **escrita** | Muitos INSERT e UPDATE | Escalar **verticalmente** (classe maior); só uma instância escreve | 13.2, 13.9 |
| Conexões | Milhares de clientes abrindo conexão | [[RDS Proxy]] | 13.6 |

A linha de escrita é a que surpreende. Em um banco relacional tradicional existe **uma** instância que aceita escrita. Você não adiciona escritores como adiciona [[Read Replica|réplicas de leitura]]. Para escrever mais, você escolhe uma classe maior (escala vertical) ou particiona os dados entre bancos (sharding, na aplicação). [[Aurora]] melhora o desempenho de escrita da instância única e acelera o [[Failover|failover]], mas continua com um writer por cluster (no modelo que a prova cobra).

## Limites e cotas que importam

Por padrão, uma conta tem até **40 DB instances por Região**, valor que vale em conjunto para instâncias [[RDS]], [[Aurora]], [[Neptune]] e [[DocumentDB]], e que pode ser aumentado pelo [[Service Quotas]] (verificado em novembro de 2026 na página de cotas do Aurora). Também por padrão: 40 clusters Aurora por Região, 5 [[Custom Endpoint|custom endpoints]] por cluster, 20 proxies por conta. Em um cenário de [[Recuperacao de Desastres]] com banco em outra Região, o limite do [[Regiao AWS|Region]] de standby também conta (Módulo 20).

## Ciclo de vida de versões: Extended Support

Cada versão major de engine tem uma data de fim do suporte padrão. O **[[RDS]] Extended Support** deixa instâncias e clusters continuarem recebendo suporte depois dessa data, **com cobrança adicional** que começa quando a versão entra em fim de suporte padrão (verificado em novembro de 2026). A mensagem prática: manter engine antigo tem custo; planejar upgrade (com [[Blue Green Deployment|Blue/Green Deployments]], uma cópia "green" do banco para testar e trocar com pouca interrupção) é parte do trabalho.

**Palavras-chave em inglês e o que apontam:**

- "LEAST [[Overhead Operacional|operational overhead]]" para banco relacional: [[RDS]] ou [[Aurora]], nunca banco em [[EC2]].
- "managed relational database", "automatic backups", "patching": [[RDS]].
- "minimal code changes", "migrate Oracle/SQL Server to AWS": mesmo engine no [[RDS]] (homogênea).
- "need OS-level access" para Oracle ou SQL Server: [[RDS Custom]].
- "reduce licensing costs": migrar de Oracle ou SQL Server para PostgreSQL ou MySQL/Aurora (heterogênea, com [[Schema Conversion Tool|SCT]] e [[DMS]]).
- "[[OLTP]]" aponta [[RDS]] ou [[Aurora]]; "analytics on petabytes" aponta [[Redshift]].

**Pegadinhas clássicas:**

- Dizer que o [[RDS]] cuida de "otimização de queries". Não: é responsabilidade do cliente.
- Confundir [[RDS Custom]] com banco em [[EC2]]. O Custom é gerenciado com acesso extra; o EC2 é totalmente seu.
- Achar que [[Multi-AZ]] cluster existe para qualquer engine. Só MySQL e PostgreSQL.

| Requisito no enunciado | Resposta provável | Por quê |
|---|---|---|
| Banco relacional com patch, backup e [[Failover\|failover]] automáticos | [[RDS]] | Serviço gerenciado, menor overhead |
| Migrar Oracle com PL/SQL sem reescrever | [[RDS]] for Oracle | [[Migracao Homogenea\|Migração homogênea]] |
| Aplicação legada precisa instalar agente no SO do SQL Server | [[RDS Custom\|RDS Custom for SQL Server]] | Acesso ao SO com automação parcial |
| Reduzir custo de licença trocando de engine | [[Aurora]] ou [[RDS]] PostgreSQL com [[Schema Conversion Tool\|SCT]] e [[DMS]] | [[Migracao Heterogenea\|Migração heterogênea]] |
| Escrita intensa em banco relacional | Classe maior (vertical) ou [[Aurora]] | Só uma instância escreve |
| Relatórios pesados atrapalhando o [[OLTP]] | [[Read Replica\|Read replica]] dedicada, depois [[Data Warehouse\|data warehouse]] | Isola a carga de leitura |

## Resumo

> [!abstract] A aula em uma frase
> O [[RDS]] troca o trabalho repetitivo de operar banco (patch, backup, [[Failover|failover]], hardware) por um serviço gerenciado, mas deixa com você o modelo de dados e as queries; a escolha do engine segue compatibilidade com a aplicação, custo de licença e recursos disponíveis.

**A lógica, em 5 passos**

1. Operar banco em [[EC2]] obriga você a cuidar de patch, backup, [[Alta Disponibilidade|HA]] e hardware.
2. O [[RDS]] assume essas tarefas; a otimização da aplicação continua sendo sua.
3. A DB instance é engine + classe + storage + endpoint [[DNS]], dentro de uma [[VPC]], em [[Sub-rede Privada|sub-redes privadas]], protegida por [[Security Group|security group]].
4. O engine se escolhe por compatibilidade (homogênea vs heterogênea), licença e recursos ([[Multi-AZ]] cluster só em MySQL e PostgreSQL).
5. Um banco relacional escala leitura com réplicas e cache, e escala escrita só verticalmente.

**Números para lembrar**

| O quê | Valor | Por que importa |
|---|---|---|
| Engines do [[RDS]] | 6 (Db2, MariaDB, SQL Server, MySQL, Oracle, PostgreSQL) | Mais o [[Aurora]], que tem guia próprio |
| DB instances por Região (padrão) | 40, compartilhado com [[Aurora]], [[Neptune]] e [[DocumentDB]] | Cota ajustável no [[Service Quotas]] |
| [[Sub-rede\|Sub-redes]] do [[DB Subnet Group\|DB subnet group]] | Pelo menos 2, em 2 [[Zona de Disponibilidade\|AZs]] | Habilita [[Multi-AZ]] |
| Oracle License Included | Só SE2 | Enterprise exige [[BYOL]] |

**Na prática, isso significa**

- "Menor overhead" com banco relacional pede [[RDS]] ou [[Aurora]].
- Mesmo engine é migração fácil; trocar de engine exige [[Schema Conversion Tool|SCT]] e [[DMS]].
- Acesso ao sistema operacional do banco pede [[RDS Custom]] ou [[EC2]].
- Mais escrita pede máquina maior, não mais escritores.

## Erros comuns

- **"O [[RDS]] faz tuning das minhas queries."** Não faz. Ele oferece ferramentas de diagnóstico ([[Performance Insights]], hoje dentro do [[CloudWatch]] Database Insights, conforme a documentação), mas o ajuste é seu.
- **"Posso entrar por SSH no [[RDS]]."** Não pode. Sem acesso ao host, a menos que você use [[RDS Custom]].
- **"Um banco relacional escala escrita adicionando réplicas."** Réplicas servem leitura. Escrita escala para cima.
- **"[[Multi-AZ]] cluster existe para todos os engines."** Existe só para MySQL e PostgreSQL.
- **"Trocar Oracle por PostgreSQL é só apontar a string de conexão."** É [[Migracao Heterogenea|migração heterogênea]]: converte-se schema e código.

## Pratique

**1.** Uma empresa executa um banco PostgreSQL em [[EC2|instâncias EC2]] e gasta muito tempo com patches, backups e [[Failover|failover]] manual. A equipe quer reduzir o [[Overhead Operacional|esforço operacional]] sem trocar de engine nem mudar a aplicação. Qual solução atende?

- [ ] a) Migrar para o Amazon RDS for PostgreSQL com Multi-AZ
- [ ] b) Migrar para o Amazon Aurora MySQL, convertendo o schema e o código da aplicação
- [ ] c) Usar instâncias EC2 maiores com scripts de backup agendados
- [ ] d) Manter o PostgreSQL em EC2 e adicionar uma réplica configurada manualmente

**2.** Uma equipe migrou o banco do sistema de pedidos de [[EC2]] para o [[RDS|Amazon RDS]] e acredita que a AWS agora também vai resolver as consultas lentas da aplicação. Qual tarefa continua sendo responsabilidade do cliente?

- [ ] a) Aplicar patches de sistema operacional na instância do banco
- [ ] b) Substituir o hardware que falhar no datacenter
- [ ] c) Executar o failover para o standby quando a zona falhar
- [ ] d) Criar índices e ajustar as consultas lentas

**3.** Uma empresa precisa instalar um agente de monitoramento de terceiros diretamente no sistema operacional da instância de um banco Oracle, mas quer manter o máximo possível de automação gerenciada. O que usar?

- [ ] a) Amazon RDS for Oracle padrão, com Multi-AZ ativado
- [ ] b) Amazon RDS Custom for Oracle, que dá acesso ao sistema operacional
- [ ] c) Oracle instalado em uma instância EC2, com acesso total ao host
- [ ] d) Amazon Aurora PostgreSQL, com conversão de schema

**4.** Uma aplicação interna usa Microsoft SQL Server com stored procedures em T-SQL. A empresa quer migrar para a AWS com o MENOR esforço de alteração no código. Qual opção atende?

- [ ] a) Reescrever a aplicação para Amazon Aurora PostgreSQL
- [ ] b) Migrar os dados para o Amazon DynamoDB
- [ ] c) Converter o schema com a Schema Conversion Tool para MySQL
- [ ] d) Amazon RDS for SQL Server, mantendo o mesmo engine

**5.** Uma empresa vai migrar um banco Oracle com procedures em PL/SQL para o [[Aurora|Amazon Aurora]] PostgreSQL, para eliminar o custo de licenças. Como essa migração é classificada e o que ela exige?

- [ ] a) Heterogênea: muda o engine e exige converter schema e código
- [ ] b) Homogênea: basta restaurar um snapshot do Oracle no Aurora, sem conversão
- [ ] c) Homogênea: é uma atualização de versão minor dentro do mesmo engine
- [ ] d) Heterogênea, mas sem conversão, porque o Aurora aceita PL/SQL nativamente

**6.** Uma empresa quer reduzir o custo de licenças de banco de dados de um sistema de pedidos e aceita converter o schema. Qual abordagem é mais adequada?

- [ ] a) Manter o Oracle Enterprise Edition no RDS com License Included
- [ ] b) Migrar para o RDS for SQL Server com License Included
- [ ] c) Migrar para RDS for PostgreSQL ou Aurora, com SCT e DMS
- [ ] d) Rodar o Oracle em instâncias EC2 em Dedicated Hosts

**7.** Uma equipe cria um [[RDS]] for MySQL na [[VPC]] e quer que o serviço consiga posicionar o standby do [[Multi-AZ]] em uma segunda [[Zona de Disponibilidade|AZ]]. Qual componente define em quais [[Sub-rede|sub-redes]] o RDS pode colocar a instância?

- [ ] a) O security group da instância, com as regras de entrada e saída
- [ ] b) O DB subnet group, com sub-redes em pelo menos duas AZs
- [ ] c) O parameter group, com os parâmetros de ajuste do engine

**13.** Uma empresa precisa de um banco relacional com acesso ao sistema operacional para uma aplicação empacotada de terceiros que só funciona com SQL Server. Qual alternativa oferece menos overhead que o [[EC2]], mantendo o acesso ao host?

- [ ] a) RDS for SQL Server padrão, sem personalização
- [ ] b) Amazon Aurora PostgreSQL, com conversão de schema
- [ ] c) SQL Server instalado em EC2, com acesso total ao host
- [ ] d) RDS Custom for SQL Server, com acesso ao host

> [!success]- Gabarito
> **1. a)** [[RDS]] for PostgreSQL com [[Multi-AZ]] mantém o engine e assume patch, backup e [[Failover|failover]]. [[Aurora]] MySQL (b) exige converter schema e código; [[EC2]] maior com scripts (c) mantém o trabalho operacional; réplica manual em EC2 (d) também.
> **2. d)** Índices e ajuste de consultas são do cliente. Patch de SO (a), hardware (b) e [[Failover|failover]] (c) são da AWS no [[RDS]].
> **3. b)** [[RDS Custom]] dá acesso ao SO e ao banco com automação parcial. O [[RDS]] padrão (a) bloqueia o host; Oracle em [[EC2]] (c) devolve toda a administração a você; [[Aurora]] PostgreSQL (d) é outro engine.
> **4. d)** Mesmo engine no [[RDS]] evita reescrever T-SQL. Reescrever para [[Aurora]] PostgreSQL (a), migrar para [[DynamoDB]] (b) e converter para MySQL com [[Schema Conversion Tool|SCT]] (c) são migrações com mudança de código.
> **5. a)** Oracle para [[Aurora]] PostgreSQL muda de engine: heterogênea, com conversão de schema e código ([[Schema Conversion Tool|SCT]] e [[DMS]]). Restaurar [[Snapshot|snapshot]] Oracle no Aurora (b) não é possível, minor (c) não muda engine e o Aurora não executa PL/SQL nativamente (d).
> **6. c)** PostgreSQL ou [[Aurora]] eliminam a licença comercial, com [[Schema Conversion Tool|SCT]] e [[DMS]] para converter e migrar. Oracle Enterprise com License Included (a) não existe e mantém custo; SQL Server License Included (b) continua pagando licença; [[Dedicated Host|Dedicated Hosts]] (d) aumentam custo.
> **7. b)** O [[DB Subnet Group|DB subnet group]] define as [[Sub-rede|sub-redes]] (em pelo menos duas [[Zona de Disponibilidade|AZs]]) onde o [[RDS]] posiciona a instância. Regras de tráfego (a) são do [[Security Group|security group]]; parâmetros (c) são do [[Parameter Group|parameter group]]; recursos opcionais (d) são do option group.
> **8. b)** Com um único writer, escrever mais exige classe maior. Read replicas (a) e cache (d) só ajudam leitura; [[Multi-AZ]] (c) dá [[Disponibilidade|disponibilidade]], não escala de escrita.
> **9. a)** O [[Multi-AZ DB Cluster|Multi-AZ DB cluster]] existe só para MySQL e PostgreSQL; MariaDB, Oracle, SQL Server e Db2 ficam de fora. As demais opções (b, c, d) são falsas.
> **10. c)** O [[Redshift]] é o [[Data Warehouse|data warehouse]] [[Armazenamento Colunar|colunar]] para análises pesadas. [[RDS Custom]] (a) é para acesso ao SO; [[DynamoDB]] com [[DAX]] (b) é NoSQL com cache; mais [[gp3]] (d) não resolve consulta analítica sobre terabytes.
> **11. a), c)** O Oracle LI vale só para SE2, e o SQL Server tem License Included em várias edições. A opção b) é falsa (Enterprise exige [[BYOL]]), d) é falsa (PostgreSQL não tem taxa de licença) e e) é falsa (a instância sempre é cobrada).
> **12. a), b)** Acesso ao SO ou ao host de Oracle e SQL Server é o caso do [[RDS Custom]]. Menor overhead em PostgreSQL (c) é [[RDS]] padrão; trocar engine (d) é [[Migracao Heterogenea|migração heterogênea]]; múltiplos writers (e) não existe no RDS.
> **13. d)** [[RDS Custom|RDS Custom for SQL Server]] dá acesso ao host com mais automação que o [[EC2]]. O [[RDS]] padrão (a) não dá acesso ao SO; [[Aurora]] PostgreSQL (b) não roda SQL Server; SQL Server em EC2 (c) tem mais overhead que o pedido.
