# Aula 23.8: Storage Gateway e o armazenamento híbrido

[[23 - Migracao e Transferencia de Dados|Voltar ao módulo]]

> [!question] E se a empresa não quer migrar a aplicação agora, mas quer usar o S3 como armazenamento infinito e barato por trás dela, sem reescrever nada?

## O problema: nem tudo muda de uma vez

Até aqui, o módulo tratou de **mover**: servidores com o [[Application Migration Service|MGN]], bancos com o [[DMS]], arquivos com o [[DataSync]], remessas com a [[Snow Family|Família Snow]]. Mas há um terceiro cenário, muito comum: a aplicação **fica no datacenter** (por [[Latencia|latência]], por licença, por inércia, porque o fornecedor não suporta nuvem), e a empresa só quer trocar o **armazenamento** por trás dela.

Exemplos reais:

- Um servidor de arquivos Windows está sem espaço, e comprar mais SAN custa caro.
- O backup em fita consome salas, caminhões e gente, e ninguém testa a restauração.
- Uma aplicação de imagens médicas precisa de baixa [[Latencia|latência]] para os exames dos últimos meses, mas guarda 10 anos de histórico que quase ninguém abre.

A resposta da AWS para **armazenamento híbrido** é o [[Storage Gateway]]: um aparelho (virtual ou físico) que roda no seu ambiente, fala os protocolos que suas aplicações já conhecem ([[NFS]], [[SMB]], [[iSCSI]]) e guarda os dados na AWS, com um **cache local** para o que é acessado com frequência.

A ideia por trás: a aplicação enxerga um disco ou um compartilhamento local, e o fundo desse disco é a nuvem.

## Os tipos de gateway

O [[Storage Gateway]] tem quatro tipos (um deles fechado para novos clientes). Para escolher, a pergunta é: **qual protocolo a aplicação fala?**

| Tipo | Protocolo para a aplicação | Armazenamento na AWS | Situação |
|---|---|---|---|
| **[[S3 File Gateway]]** | [[NFS]] e [[SMB]] | Objetos no [[S3]] | Ativo |
| **FSx [[S3 File Gateway\|File Gateway]]** | [[SMB]] | [[FSx]] for Windows File Server | Fechado para novos clientes |
| **[[Volume Gateway]]** | [[iSCSI]] (blocos) | [[S3]], com [[Snapshot\|snapshots]] do [[EBS]] | Ativo |
| **[[Tape Gateway]]** | [[iSCSI]] (fita virtual, VTL) | [[S3]] Glacier e [[S3 Glacier Deep Archive\|Deep Archive]] | Ativo |

> [!warning] FSx File Gateway
> A documentação atual indica que o **[[FSx]] [[S3 File Gateway|File Gateway]] está fechado para novos clientes** (verificado em novembro de 2026). Ele ainda aparece em materiais de prova antigos. A alternativa recomendada para acesso local a arquivos em FSx é acessar o [[FSx for Windows File Server|FSx for Windows]] diretamente (por [[Direct Connect]] ou VPN) ou usar o S3 File Gateway quando o [[S3]] serve.

### S3 File Gateway

Expõe um **compartilhamento de arquivos** ([[NFS]] para Linux, [[SMB]] para Windows) cujos arquivos são gravados como **objetos** em um [[Bucket|bucket]] do [[S3]]. Para a aplicação, é uma pasta de rede; para a AWS, cada arquivo é um objeto, que pode então ser usado por serviços nativos: análise com Athena, processamento com Lambda, [[Replicacao do S3|replicação entre Regiões]], e as **classes de armazenamento e [[Lifecycle Policy|regras de ciclo de vida]]** do S3 (veja o [[11 - Amazon S3 a Fundo|Módulo 11]]).

Características principais:

- **[[Cache]] local** dos dados acessados recentemente, para baixa [[Latencia|latência]].
- Os objetos podem ser gravados nas classes **[[S3]] Standard, [[S3 Standard-IA|Standard-IA]], One Zone-IA e [[S3 Intelligent-Tiering|Intelligent-Tiering]]**. A ida ao **Glacier** acontece por **[[Lifecycle Policy|regra de ciclo de vida]]**, nunca direto pelo gateway.
- Metadados do arquivo (dono, permissões) preservados como metadados do objeto.
- Pode usar **[[Active Directory]]** para autenticação [[SMB]].
- Útil para: backups e arquivamento de arquivos, data lakes alimentados por sistemas locais, deslocar arquivos "frios" para o [[S3]] sem mudar o caminho que as aplicações usam.

> [!example] Servidor de arquivos sem espaço
> Uma agência tem um servidor Windows com 20 TB de projetos antigos que raramente são abertos. Em vez de comprar mais disco, ela implanta um [[S3 File Gateway]] como VM, mapeia o [[SMB|compartilhamento SMB]] nos computadores e move as pastas antigas para ele. Os arquivos aparecem nos mesmos caminhos. O [[S3]] guarda o histórico, e uma [[Lifecycle Policy|regra de ciclo de vida]] o move para classes mais baratas depois de 90 dias. O cache local mantém os arquivos recentes rápidos.

### Volume Gateway

Apresenta **volumes de blocos** por **[[iSCSI]]** (um disco que o sistema operacional monta como se fosse local). Dois modos, e a diferença é onde fica a cópia **primária**:

| Modo | Dados primários | O que vai para a AWS | Quando usar |
|---|---|---|---|
| **Cached** | No [[S3]] (AWS) | Todos os dados; o cache local guarda os acessados com frequência | Quer reduzir o armazenamento local, com acesso rápido ao que é quente |
| **Stored** | Localmente (todo o conjunto) | Cópia assíncrona do todo, como [[Snapshot\|snapshots]] do [[EBS]] | Precisa de baixa [[Latencia\|latência]] para **todo** o conjunto, com backup na nuvem |

A frase que decide a prova: **cached = dados no [[S3]], cache local; stored = dados locais, backup no S3**. No modo stored, os [[Snapshot|snapshots]] viram **snapshots do [[EBS]]**, que podem ser restaurados como volumes EBS em uma [[EC2|instância EC2]]: se o datacenter cair, a aplicação sobe na AWS com o último snapshot, o que é a pegadinha clássica de DR com o [[Volume Gateway]] (um caminho de [[Recuperacao de Desastres|recuperação de desastres]], que se conecta com o [[Elastic Disaster Recovery]] do módulo de resiliência).

### Tape Gateway

Substitui fitas e robôs de fita. A aplicação de backup (as ferramentas de mercado como Veeam, Veritas, Commvault e outras, dentro da lista de compatibilidade da AWS) enxerga uma **[[Tape Gateway|biblioteca de fitas virtuais]] (VTL)** por [[iSCSI]]. As fitas virtuais ficam no [[S3]] e podem ser **arquivadas** no S3 Glacier ou no [[S3 Glacier Deep Archive|Deep Archive]], bem mais baratos.

Por que importa: elimina transporte e armazenamento físico de fitas, mantém o **mesmo processo de backup** (nada a reescrever), e os dados ficam duráveis na AWS. Cenário clássico da prova: "a empresa tem backup em fitas físicas caras e quer migrar para a nuvem **sem mudar o software de backup**": [[Tape Gateway]].

## Como o gateway funciona por dentro

### Onde roda

O gateway é um **appliance** com três formas de implantação:

| Forma | Descrição |
|---|---|
| **Máquina virtual** | Em VMware ESXi, Microsoft Hyper-V ou Linux KVM, no seu datacenter |
| **Instância [[EC2]]** | Dentro da AWS, útil para acesso de aplicações na nuvem a fitas ou volumes |
| **Appliance de hardware** | Servidor físico pedido à AWS, para locais sem infraestrutura de virtualização |

### Cache e buffer

O gateway precisa de **discos locais** para duas funções: o **cache** (dados acessados recentemente, servidos com baixa [[Latencia|latência]]) e o **buffer de upload** (dados à espera de serem enviados à AWS). Dimensionar esses discos errado é a causa mais comum de desempenho ruim em projetos reais.

### Como se conecta

O gateway se comunica com a AWS pela internet, por um **[[VPC Endpoint|VPC endpoint]]** (via [[Direct Connect]] ou [[Site-to-Site VPN]]), e pode ser monitorado pelo [[CloudWatch]]. A comunicação é criptografada em trânsito, e os dados no [[S3]] são criptografados em repouso (por padrão [[SSE-S3]], ou com chave do [[KMS]]).

> [!info] Ligando os pontos
> O [[Storage Gateway]] é o **oposto** do [[Snowball Edge]] e do [[DataSync]] em um ponto: aqueles movem dados uma vez (ou de tempos em tempos); o gateway é uma **ponte permanente**, com a aplicação continuando no local. Na árvore de decisão da aula 23.10, "a aplicação fica no local e precisa de acesso contínuo ao [[S3]] com cache" aponta para o Storage Gateway.

## Storage Gateway, DataSync e Transfer Family: a comparação que cai na prova

| Característica | [[Storage Gateway]] | [[DataSync]] | [[Transfer Family]] |
|---|---|---|---|
| Natureza | Acesso híbrido contínuo, com cache | Cópia e sincronização de dados | Recepção por protocolo de parceiro |
| Aplicação local | Continua usando arquivos, volumes ou fitas | Não muda; os dados são copiados | Parceiros enviam por SFTP, FTPS, FTP, AS2 |
| Destino | [[S3]], [[EBS]] ([[Snapshot\|snapshots]]), Glacier | S3, [[EFS]], [[FSx]], outros | S3 e EFS |
| Quando | Aplicação fica no local, armazenamento na nuvem | Migração ou sincronização agendada | Fluxo de arquivos de terceiros |

## Laboratório (opcional)

> [!warning] Use uma conta AWS pessoal separada
> Faça este laboratório em uma **[[Conta AWS|conta AWS]] pessoal**, com o [[Budgets|AWS Budgets]] configurado, **nunca na conta de produção da empresa**. Um gateway em [[EC2]] e os volumes de cache geram custo por hora.

Objetivo: entender o fluxo de criação de um [[S3 File Gateway]].

1. No console do [[Storage Gateway]], escolha **Create gateway** e o tipo **[[S3|Amazon S3]] [[S3 File Gateway|File Gateway]]**.
2. Escolha a plataforma de hospedagem (por exemplo, [[EC2|Amazon EC2]] para o teste) e siga o assistente.
3. Adicione discos para cache e buffer de upload.
4. Crie um compartilhamento de arquivos associado a um [[Bucket|bucket]] do [[S3]].
5. Monte o compartilhamento ([[NFS]] ou [[SMB]]) em uma instância cliente e grave um arquivo.
6. Confirme que o arquivo aparece como objeto no [[Bucket|bucket]].

Custo estimado: baixo, mas contínuo enquanto o gateway existir. **Limpeza**: apague o compartilhamento, o gateway, a instância e o [[Bucket|bucket]] no mesmo dia.

**Padrões de cenário:**

- "Aplicação local precisa guardar arquivos no [[S3]] mantendo [[NFS]] ou [[SMB]]": [[S3 File Gateway]].
- "Backup em fitas físicas e quer migrar sem mudar o software": [[Tape Gateway]].
- "Disco [[iSCSI]] com dados na nuvem e cache local dos mais usados": [[Volume Gateway|Volume Gateway cached]].
- "Conjunto inteiro precisa de baixa [[Latencia|latência]] local, com backup assíncrono na nuvem": [[Volume Gateway|Volume Gateway stored]].
- "Reduzir o armazenamento local sem migrar a aplicação": qualquer gateway, conforme o protocolo.

**Palavras-chave:** *hybrid storage*, *on-premises application*, *[[NFS]]*, *[[SMB]]*, *[[iSCSI]]*, *virtual tape library*, *local cache*, *low [[Latencia|latency]]*.

**Pegadinhas:**

- **Cached versus stored**: onde fica a cópia primária.
- **[[S3 File Gateway]] não é [[DataSync]]**: é acesso contínuo, não uma cópia agendada.
- **[[Tape Gateway]] usa [[iSCSI]] e VTL**, não protocolos de arquivo.
- **[[FSx]] [[S3 File Gateway|File Gateway]] está fechado para novos clientes.**
- [[Volume Gateway]] fala **blocos ([[iSCSI]])**, não [[NFS]] ou [[SMB]].

| Requisito no enunciado | Resposta provável | Por quê |
|---|---|---|
| Arquivos [[NFS]]/SMB locais gravando no [[S3]] | [[S3 File Gateway]] | Objetos no S3 com cache local |
| Substituir biblioteca de fitas sem trocar o software | [[Tape Gateway]] | VTL via [[iSCSI]], arquivada em Glacier |
| Volume [[iSCSI]], dado primário na nuvem | [[Volume Gateway\|Volume Gateway cached]] | [[Cache]] local do que é quente |
| Volume [[iSCSI]], tudo local e backup na AWS | [[Volume Gateway\|Volume Gateway stored]] | [[Snapshot\|Snapshots]] assíncronos |
| Aplicação Windows quer acessar [[FSx for Windows File Server\|FSx for Windows]] de um local, sem gateway | Acesso direto ao [[FSx]] por [[Direct Connect]] ou VPN | Alternativa moderna ao FSx [[S3 File Gateway\|File Gateway]], que está fechado para novos clientes |
| Arquivos do gateway para o Glacier | [[S3 File Gateway]] mais [[Lifecycle Policy\|regra de ciclo de vida]] | O gateway não grava direto no Glacier |

## Resumo

> [!abstract] A aula em uma frase
> O [[Storage Gateway]] é a ponte permanente entre aplicações que ficam no datacenter e o armazenamento da AWS: o protocolo que a aplicação fala ([[NFS]] ou [[SMB]], [[iSCSI]] de volume, iSCSI de fita) escolhe o tipo de gateway, e o cache local cuida da [[Latencia|latência]].

**A lógica, em 5 passos**

1. A aplicação fica no local, mas o armazenamento vai para a nuvem.
2. Um appliance (VM, [[EC2]] ou hardware) fala os protocolos locais.
3. O [[S3 File Gateway]] guarda arquivos como objetos; o [[Volume Gateway]] guarda blocos com [[Snapshot|snapshots]]; o [[Tape Gateway]] guarda fitas virtuais.
4. O cache local mantém o que é quente rápido.
5. O destino na AWS entrega [[Durabilidade|durabilidade]] e classes de armazenamento baratas.

**Números para lembrar**

| O quê | Valor | Por que importa |
|---|---|---|
| Tipos de gateway | 4 ([[FSx]] [[S3 File Gateway\|File Gateway]] fechado) | Escolha pelo protocolo |
| [[Volume Gateway]] | 2 modos: cached e stored | Onde fica o dado primário |
| Implantação | VM, [[EC2]] ou hardware | Opções de hospedagem |

**Tabela-síntese**

| Gateway | Protocolo | Destino |
|---|---|---|
| [[S3]] File | [[NFS]] e [[SMB]] | Objetos no S3 |
| Volume cached | [[iSCSI]] | [[S3]] (cache local) |
| Volume stored | [[iSCSI]] | Local, [[Snapshot\|snapshots]] no [[S3]] |
| Tape | [[iSCSI]] [[Tape Gateway\|VTL]] | [[S3]] Glacier e [[S3 Glacier Deep Archive\|Deep Archive]] |

**Na prática, isso significa**

- Escolher o gateway pelo protocolo da aplicação.
- Dimensionar bem o cache e o buffer de upload.
- Responder [[Tape Gateway]] sempre que houver backup em fita sem troca de software.

## Erros comuns

- **Confundir [[Volume Gateway|Volume Gateway cached]] com stored.** O primeiro mantém o dado primário na AWS; o segundo, no local.
- **Usar [[Storage Gateway]] para uma migração única.** Para isso, o [[DataSync]].
- **Subdimensionar o cache.** A [[Latencia|latência]] sobe e a aplicação reclama.
- **Esperar [[NFS]] no [[Tape Gateway]].** Ele usa [[iSCSI]].
- **Indicar [[FSx]] [[S3 File Gateway|File Gateway]] para um projeto novo.** Está fechado para novos clientes.

## Pratique

**1.** Uma aplicação Linux local precisa gravar arquivos por [[NFS]] e guardá-los no [[S3]], mantendo baixa [[Latencia|latência]] para os arquivos recentes. O que usa?

- [ ] a) AWS DataSync, que copia e sincroniza dados
- [ ] b) Amazon S3 File Gateway
- [ ] c) AWS Transfer Family
- [ ] d) Amazon EFS direto

**2.** Uma empresa tem backups em fitas físicas e quer migrar para a nuvem sem trocar o software de backup. Qual solução atende?

- [ ] a) Tape Gateway
- [ ] b) S3 Transfer Acceleration
- [ ] c) Snowball Edge
- [ ] d) AWS Config

**3.** Qual modo do [[Volume Gateway]] mantém o conjunto de dados primário no armazenamento local, com cópias assíncronas na AWS?

- [ ] a) Cached
- [ ] b) Stored
- [ ] c) Tape
- [ ] d) File

**4.** Uma empresa quer reduzir o espaço de disco local. Os dados ficam na AWS e só os mais acessados ficam em cache local, via [[iSCSI]]. Qual configuração?

- [ ] a) Volume Gateway no modo stored
- [ ] b) S3 File Gateway
- [ ] c) Volume Gateway no modo cached
- [ ] d) Tape Gateway

**5.** (Escolha DUAS.) Quais são formas de implantar o appliance do [[Storage Gateway]]?

- [ ] a) Máquina virtual no VMware ESXi ou Hyper-V
- [ ] b) Instância do Amazon EC2
- [ ] c) Função do AWS Lambda
- [ ] d) Contêiner no Amazon ECS com Fargate
- [ ] e) Ambiente do AWS Elastic Beanstalk

**6.** Uma equipe precisa migrar 50 TB de arquivos para o [[S3]] uma única vez, com verificação de integridade. O [[Storage Gateway]] é a melhor escolha?

- [ ] a) Sim, é o serviço padrão de migração de dados da AWS para qualquer carga
- [ ] b) Sim, pois o Tape Gateway copia arquivos
- [ ] c) Não, o DataSync é indicado para cópia e sincronização
- [ ] d) Não, só o Snowmobile faz isso

**7.** Uma empresa usa um [[Volume Gateway]] no modo stored. O datacenter fica inoperante por dias e a aplicação precisa voltar rápido. Como recuperar?

- [ ] a) Reiniciar o gateway dentro da própria AWS, que recria os discos sozinho
- [ ] b) Pedir os dados em fitas ao Tape Gateway e restaurar no EC2
- [ ] c) Usar o DataSync para copiar os volumes do datacenter parado
- [ ] d) Restaurar os snapshots do EBS gerados pelo gateway como volumes e anexá-los a instâncias EC2

**8.** Que protocolo uma aplicação de backup usa para acessar a [[Tape Gateway|biblioteca de fitas virtuais]] do Tape Gateway?

- [ ] a) iSCSI
- [ ] b) SMB
- [ ] c) NFS
- [ ] d) SFTP

**9.** (Escolha DUAS.) Quais benefícios o [[S3 File Gateway]] oferece?

- [ ] a) Arquivos acessíveis por NFS ou SMB e armazenados como objetos no S3
- [ ] b) Uso de regras de ciclo de vida do S3 sobre os arquivos
- [ ] c) Substituição de um banco relacional por DynamoDB
- [ ] d) Tradução automática de esquemas de banco
- [ ] e) Execução de instâncias EC2 locais

**10.** Um gateway recém-implantado tem desempenho ruim na leitura dos arquivos recentes. Qual a causa mais provável a investigar?

- [ ] a) Ausência de um balanceador de carga
- [ ] b) Bucket em outra Região do planeta
- [ ] c) Falta de uma chave do KMS
- [ ] d) Cache local subdimensionado

> [!success]- Gabarito
> **1. b)** O [[S3 File Gateway]] fala [[NFS]] e grava objetos no [[S3]], com cache local. a) migra dados, não dá acesso contínuo; c) recebe protocolos de parceiros; d) o [[EFS]] direto não grava no S3.
> **2. a)** O [[Tape Gateway]] apresenta uma VTL via [[iSCSI]] ao software de backup. b) acelera upload; c) é transferência física; d) audita configuração.
> **3. b)** No modo stored, o conjunto primário fica local, com [[Snapshot|snapshots]] assíncronos na AWS. a) é o oposto; c) e d) são outros tipos de gateway.
> **4. c)** No cached, o dado primário fica no [[S3]] e o cache guarda o que é quente, via [[iSCSI]]. a) mantém tudo local; b) fala arquivos, não blocos; d) é para fitas.
> **5. a) e b)** O appliance roda em VM ou em [[EC2|instância EC2]] (e também em hardware dedicado). c) uma [[Lambda|função Lambda]] não hospeda o appliance; d) o [[Fargate]] não é plataforma suportada; e) o [[Elastic Beanstalk]] orquestra aplicações web, não o appliance.
> **6. c)** O [[DataSync]] é o serviço de cópia e sincronização com verificação. a) o gateway é acesso contínuo; b) o [[Tape Gateway]] é para fitas; d) o Snowmobile foi descontinuado.
> **7. d)** No modo stored, os [[Snapshot|snapshots]] viram snapshots do [[EBS]] e podem ser restaurados como volumes em [[EC2]] (padrão de DR). a) o gateway não recria discos sozinho; b) o [[Tape Gateway]] é outro tipo, para fitas; c) o datacenter está inoperante, então não há origem para copiar.
> **8. a)** O [[Tape Gateway]] usa [[iSCSI]] para a VTL. c) e b) são protocolos de arquivo do [[S3 File Gateway]]; d) é do [[Transfer Family]].
> **9. a) e b)** Acesso por [[NFS]] ou [[SMB]] com objetos no [[S3]], e [[Lifecycle Policy|regras de ciclo de vida]] aplicáveis. c) e d) são do [[DMS]] e da [[Schema Conversion Tool|SCT]]; e) é do Outposts ou Snow.
> **10. d)** O cache local guarda os dados recentes, e subdimensioná-lo eleva a [[Latencia|latência]]. b) a Região do [[Bucket|bucket]] afeta o upload, não o cache; c) e a) não afetam a leitura local.
